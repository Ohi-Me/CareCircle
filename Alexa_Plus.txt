======================================================================
0. THE MOST IMPORTANT DECISION
======================================================================

Build a new, focused Alexa+-style agent experience around a real MCP server.
Do not start with a generic chatbot, and do not depend on getting access to
Amazon's private Alexa+ preview tools.

The hackathon FAQ currently says the Alexa+ Add-on developer tools (Category SDK,
MCP Toolkit, CLI and Web Simulator) are select-partner preview tools and are not
available to hackathon participants. It says participants should build a
self-hosted MCP server or Agent Skill and demonstrate it through their own web
front end/simulator. The FAQ specifically says a web page acting as a real MCP
client—sending initialize, tools/list and tools/call requests over Streamable
HTTP—satisfies the simulated-experience path.

Therefore, the safest plan is:

1. Build a real MCP server using the required MCP specification version.
2. Use Streamable HTTP transport.
3. Build your own web client that genuinely speaks MCP to your server.
4. Give the client a conversational, voice-assistant-style experience.
5. Demonstrate the model/agent choosing tools, calling them, changing real
   application state, and reporting the outcome.
6. Clearly label it as an independent Alexa+-style simulation; do not claim that
   it is connected to a real Alexa+ device or Amazon's gated developer console.

The official hackathon rules specify MCP spec 2025-11-25 or later for the
self-hosted MCP route. Confirm that your chosen SDK supports the required version
and transport. Do not accidentally implement only legacy HTTP+SSE.

2. RECOMMENDED PROJECT
======================================================================

Working title:
DAYFLOW — A CONVERSATIONAL PERSONAL OPERATIONS AGENT

Possible polished name alternatives:
- DayFlow
- Homebase Agent
- LifeOps
- Intent-to-Action
Pick one name after checking availability. Do not spend days on naming.

One-sentence pitch:
DayFlow turns a person's everyday requests into safe, coordinated actions across
their tasks, schedule, shopping list and personal notes—using an MCP-powered
agent that remembers relevant application state, checks constraints, asks for
clarification when necessary, and verifies each action.

The core is not "ask an AI a question." The core is "ask for an outcome and watch
the agent perform and verify the steps."

Example user request:
"I have a project review tomorrow, two assignments due Friday, and 90 minutes
free today. Plan my work, add the tasks I am missing, and make sure I have the
items I need for dinner."

Possible response/workflow:
1. Read the user's existing tasks and schedule.
2. Detect missing information (for example, no time was provided for the review).
3. Ask one concise clarification if that information changes the plan.
4. Estimate available time and prioritize tasks against deadlines.
5. Create or update the relevant task records using MCP tools.
6. Add missing grocery items to a persistent list, but do not place an order or
   spend money without explicit confirmation.
7. Show a proposed plan, list every action actually completed, and provide a
   short audit trail.
8. If a tool fails, report the failure honestly and offer a retry.

The final product should be a narrow, polished workflow, not a sprawling
"AI that does everything" product.

Why this concept:
- It demonstrates multi-step tool orchestration, not one-turn Q&A.
- It has persistent state and a useful context-aware experience.
- It can be demoed without physical hardware.
- It has real actions that a judge can verify.
- It allows measurable tests and graceful failure handling.
- It can use the MCP protocol directly from a web client.
- It can be extended with one AWS service for the AWS Builder mini-challenge.

Important product discipline:
Start with tasks + schedule + shopping list. Personal notes are an optional
fourth source. Do not build real calendar integrations, email integrations,
payments or shopping checkout until the core flow works. Seed local demo data
first; label it as demo data. A real external integration can be added later only
if access is reliable and it adds clear value.

Primary-track requirement from the event:
- A working Agent Skill OR a self-hosted MCP server.
- MCP spec 2025-11-25 or later and Streamable HTTP for the self-hosted MCP route.

- Build your own front end/simulator.

- It should send real initialize, tools/list and tools/call messages over
  Streamable HTTP.

Minimum proof in the code:
1. MCP server starts and exposes an HTTP endpoint.
2. The client sends an MCP initialize request.
3. The client discovers tools through tools/list.
4. The agent/client calls one or more tools using tools/call.
5. Tool calls execute actual application logic and return structured results.
6. The results change persistent state or produce a verifiable outcome.
7. The UI displays the action/result and handles errors.
8. README and demo explain which parts are simulated and which integrations are
   real.

Do not:
- Only mention MCP in the README.
- Create an ordinary REST API and call it MCP without implementing the protocol.
- Fake tool calls in the UI.
- Hard-code a success message when no action was performed.
- Claim the project is deployed to Alexa+ or connected to an Echo device.
- Depend on access to the gated Alexa+ web simulator/CLI.

If you implement a real MCP server and an MCP-aware web client, the simulated
front end can still be attractive and product-like without pretending to be the
official Alexa+ interface.

5. TOOL DESIGN — MCP TOOLS THE AGENT CAN CALL
======================================================================

Use small, explicit tools. Avoid one giant "do_everything" tool.

Tool 1: list_tasks
Input:
- status: optional "open", "done", or "all"
- due_before: optional ISO date
Output:
- list of tasks with id, title, due date, priority, estimated minutes, status

Tool 2: create_task
Input:
- title: required string
- due_date: optional ISO date/time
- priority: "low", "medium", "high"
- estimated_minutes: optional positive integer
Output:
- created task record, including stable task ID

Tool 3: update_task
Input:
- task_id: required
- fields: allowed task fields only
Output:
- updated task record or a structured not-found/validation error

Tool 4: mark_task_done
Input:
- task_id: required
Output:
- updated task status

Tool 5: get_schedule
Input:
- date: ISO date
Output:
- availability blocks and existing commitments from the demo schedule

Tool 6: build_daily_plan
Input:
- date: ISO date
- available_minutes: positive integer
- task_ids: optional list
Output:
- ordered proposed plan, time estimates, conflicts and unallocated tasks
Important: planning should return a proposal; do not automatically alter the user's
calendar without consent.

Tool 7: list_shopping_items
Input:
- status: optional "needed", "all"
Output:
- items with id, name, quantity, status

Tool 8: add_shopping_item
Input:
- name: required
- quantity: optional
- reason: optional
Output:
- saved item

Tool 9: remove_shopping_item
Input:
- item_id: required
Output:
- removed/updated item or error

Optional tool 10: search_notes
Input:
- query: required
Output:
- relevant user-owned note snippets with source identifiers

Optional tool 11: summarize_actions
Input:
- task_ids and/or date
Output:
- a concise summary derived from stored state

Tool design rules:
- Every tool needs a description clear enough for an agent to select it.
- Use strict schemas and validate every argument.
- Return structured results that include success/failure.
- Do not accept arbitrary SQL or arbitrary file paths from the model.
- Do not let the model invent task IDs; IDs must come from actual tool results.
- Keep tools idempotent where possible, or guard against duplicate actions.
- Use a consistent error shape, for example: code, message, retryable.
- Log tool name, timestamp, outcome and latency without logging sensitive content
  unnecessarily.
- Confirm before destructive or costly actions.

6. ARCHITECTURE
======================================================================

Recommended architecture:

Browser UI
  |
  | natural-language request
  v
Agent/orchestration layer
  |
  | discovers tools and sends MCP JSON-RPC messages
  v
MCP client in web/backend
  |
  | Streamable HTTP, MCP initialize / tools/list / tools/call
  v
Self-hosted MCP server
  |
  | validated tool handlers
  v
Application service layer
  |
  v
SQLite database (MVP) or PostgreSQL (optional)

Optional model:
The agent uses a tool-capable LLM to interpret the request, decide which tools
are needed, inspect tool results, ask clarification and explain the final result.
Keep the tools and database deterministic even if the LLM is nondeterministic.

Recommended stack:
- Frontend: Next.js + React + TypeScript.
- Backend/MCP server: Python + FastAPI with a compatible official MCP Python SDK,
  or TypeScript/Node with a compatible MCP SDK. Pick ONE backend stack.
- Database: SQLite for the first working version; PostgreSQL only if deployment
  requires it.
- Model: a tool-calling-capable model available to you. Amazon Bedrock is a
  possible AWS Builder integration, but do not make Bedrock mandatory before
  the basic MCP flow works.
- Tests: pytest or the relevant language test framework.
- Local environment: .env for secrets; .env.example contains placeholders only.
- Hosting: any reliable host that permits the required HTTP behavior. For local
  judging, document setup. If exposing a local server, use a secure tunnel only
  for testing and never expose secrets.

MCP protocol checklist:
- Required protocol version from the hackathon rules: 2025-11-25 or later.
- Streamable HTTP transport, not only legacy HTTP+SSE.
- Initialize handshake works.
- Tool discovery works.
- Tool invocation works.
- JSON-RPC errors and application errors are handled distinctly.
- Content type, session behavior and protocol version follow the SDK/spec.
- Test from a clean client, not only from the same server code.
- Check the current SDK documentation before selecting a version; do not assume
  that an old tutorial or sample supports the required version.

Latency:
The current Alexa+ QuickStart mentions a sub-500 ms round-trip response target
for the MCP server. Treat this as a useful target for server/protocol calls.
The complete LLM planning workflow will take longer, so measure server latency
separately from model latency. Do not claim the complete conversation meets
500 ms unless measured.

8. MODEL / AGENT STRATEGY
======================================================================

Do not train a model from scratch. The hackathon does not require a trained ML
model or a numeric benchmark score. Use a capable existing model only if it
improves natural-language planning and tool selection.

Recommended agent loop:
1. Receive the user's request.
2. Identify the desired outcome and constraints.
3. If a critical detail is missing, ask a clarification.
4. Discover the available MCP tools.
5. Choose the minimum tools needed.
6. Call tools with schema-valid arguments.
7. Inspect the returned results.
8. If needed, call a second tool based on the first result.
9. Before a risky write, show a preview and ask for confirmation.
10. Verify changed state after writes.
11. Summarize actions actually completed, actions proposed and any failures.

Keep the model away from direct database access. It must call validated tools.

Fallback:
If the model provider is unavailable, the product should show an honest error or
offer a limited deterministic demo flow. Do not silently fabricate an AI answer.

Possible evaluation metrics:
- Correct tool selection.
- Tool argument validity.
- End-to-end task success.
- Correctness of resulting state.
- Appropriate clarification rate.
- Unsafe/unconfirmed action rate.
- Error recovery rate.
- Median and p95 tool latency.
- Model response latency and estimated cost.
These are recommended project metrics, not official hackathon score categories.

Suggested small evaluation set:
Create 30 test requests:
- 8 straightforward list/create/update/complete requests.
- 6 planning requests with time constraints.
- 4 requests with missing information that require clarification.
- 4 conflicting deadline or impossible-capacity requests.
- 4 duplicate or malformed requests.
- 4 tool/database/model failure scenarios.

For every test, record:
request, expected tool calls, expected state change, actual result, pass/fail,
error type and latency. Do not cherry-pick only successful examples.

10. DIFFERENTIATION — HOW NOT TO LOOK LIKE A BASIC CHATBOT
======================================================================

The official judging criteria cover technical implementation, design, potential
impact and quality/creativity of idea. The rules describe basic single-turn Q&A
and simple API wrappers as obvious concepts, while more creative examples include
multi-service orchestration, context-aware state, purchasing/media capabilities,
MCP Apps and Agent Skills.

Choose two or three of these differentiators and execute them well:

1. Context-aware planning:
   The agent reads actual existing task and schedule state before proposing an
   action. It does not respond from the prompt alone.

2. Constraint-aware scheduling:
   The agent respects available minutes, deadlines and estimated task duration.
   It flags tasks that cannot fit instead of pretending everything fits.

3. Verified actions:
   The UI shows that a tool actually changed persistent state and then confirms
   the final state by reading it back.

4. Safe confirmation:
   The agent distinguishes recommendations from actions. It asks before
   destructive, external or costly operations.

5. Honest recovery:
   A failed tool call is visible, explained and retryable. No false success.

6. Contextual memory:
   A user's saved preferences (for example, preferred focus-block length) affect
   future plans, and the UI lets the user inspect or reset those preferences.

7. Evaluation mode:
   A visible developer panel or report summarizes tool-call success across a
   small reproducible test set.

Do not add all seven if time is short. Prioritize stateful planning, verified
actions and safe recovery.
